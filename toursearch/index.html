The problem

A travel agency's website relied on a third-party tour search module. The agency did not control the data, the look, or what happened when the module broke, and had nothing of its own to offer partner agencies.

The goal was to replace the module with an in-house search on the agency's own server, then turn it into a platform other agencies can sign up for.

What I built

Search across operators

Each search is sent to every connected operator in parallel. Offers stream into the page as they arrive, with filters, sorting and a price check against the operator before a booking request.

One hotel, one card

Operators name the same hotel differently. A matcher tuned on 900+ hand-checked pairs merges them automatically; doubtful pairs wait in a review queue with one-click merge and undo.

Price warmup

Popular destinations are searched in the background, within each operator's rate limit. When the index is fresh, the search answers from it instead of waiting for live APIs.

Embeddable widget

Two lines of HTML add the whole search to any site: form, results, tour card, gallery, favourites and booking request. Three languages, two currencies, full-screen on phones.

Platform for agencies

Self-service sign-up, domain verification, a cabinet with leads, notifications by email and Telegram, plans and invoices, identity checks, support tickets and 24-hour demo sandboxes.

Operations

Admin panel for operators, catalogue and queues; alerts to a team chat; daily backups. Continuous delivery: a merged pull request reaches production in about two minutes.

How it works

Adapters know only the operator's own identifiers. Mapping to the shared catalogue happens in one place, and an architecture test stops adapters from touching the database. Adding an operator means writing an adapter, not changing search.

The hard parts

A 600 MB catalogue response

One operator's hotel endpoint repeats every hotel dozens of times; a single country came back at 602 MB. A streaming parser reads it from disk: 14,000 hotels in seven minutes at a 72 MB memory peak. The same API encodes every number as a float, so fixtures are built from raw XML.

Money is never a float

Prices are numeric(12,2) in the database and strings in PHP and JSON, compared with bccomp. Converting to a number anywhere loses cents silently, so the rule is enforced in review and tests.

No silent data loss

An unknown meal code never aborts an import. An offer for an unmatched hotel is kept and queued for matching. An empty response never wipes the catalogue. Early on I found seven losses that all looked like successful runs.

Failure stays local

If one destination keeps failing at one operator, only that pair pauses: 15 minutes, then an hour, then a block for one, three and seven days with a single probe after each. Everything else keeps running.

A widget that survives any host page

A host site set the root font size to 10px and shrank every rem-based element. The widget now renders in Shadow DOM, resets inherited styles, and the build converts rem to px. A browser test matrix runs it on different host pages.

Results that keep their place

Offers arrive in waves while the visitor scrolls. The client tells the server what it has already shown, so new offers append below instead of reshuffling what the visitor is reading.
